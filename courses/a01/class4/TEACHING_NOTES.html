OVERVIEW / GOALS

學習目標

  1. 理解如何利用單一 HTML + 響應式卡片流 (Mobile-First RWD) 滿足現場訪談的機動性。
  2. 掌握如何利用 mode: 'no-cors' 探針繞過瀏覽器跨域限制，測試客戶端防火牆放行。
  3. （核心踩坑點） 理解雲端架構的 DNS 解析機制，學會排除「DNS 網域不存在 (NXDOMAIN)」造成的假性網路阻擋。
  4. 掌握「HTML 報告數據內嵌與回載技術」，在無資料庫情況下達成完整的數據交流閉環。
UNIT 01

單元一：為什麼選擇「單一 HTML」與「行動優先 (Mobile-First)」？

1. 痛點分析

售前顧問進入企業客戶會議室時，網路往往極受限制，且需要快速查閱各平台指標。

  • 無後端/無資料庫：免去繁瑣的伺服器架構部署，100% 保障客戶企業的資安隱私，網頁下載下來直接離線即開即用。
  • 行動優先 (Mobile-First RWD)：
    • 傳統的「大矩陣表格」在手機上會被迫產生水平滾動條，極難閱讀。
    • 我們改用 「卡片流 (Card Grid)」 設計。手機上是垂直排列的溫潤水彩圓角卡片，觸控面積大；當螢幕拉寬到平板和電腦時，再利用 CSS Grid 自動擴展為雙欄或三至四欄佈局。
    • 頂部使用可單指滑動的分類列（Category Swiper），點擊快速篩選，大幅降低滾動頁面的疲勞度。
UNIT 02

單元二：瀏覽器沙盒下的網路連線檢測 (Reachability Engine)

1. CORS 限制與跨域沙盒

當我們在 file:// 或非目標伺服器的網域下，嘗試用瀏覽器對 https://api.openai.com 發送一般的 fetch() 請求時，瀏覽器會直接因為 CORS (跨來源資源共用) 安全政策而攔截回應內容，並在 Console 報出跨域錯誤。

2. 解決手段：無 CORS 連線探針 (no-cors)

為了解決這個限制，我們在 fetch 參數中加入了：

fetch(url, {
  method: "GET",
  mode: "no-cors",  // 繞過 CORS 回傳讀取限制
  cache: "no-store",
  signal: controller.signal // 超時中止控制
})
  • 原理：mode: 'no-cors' 告訴瀏覽器：「我只是想把請求發出去建立連線，我不需要、也**不讀取**你回傳的具體 JSON 回應（此時回應類型會被瀏覽器封裝為 Opaque）」。
  • 檢測邏輯：
    • 連線成功：只要 TCP/TLS 三向交握成功（不論 HTTP 狀態碼，因為無跨域權限，取得的狀態碼一律為 0），代表客戶網路**並未阻擋該網域**。
    • 受阻 (Blocked)：如果客戶網路被防火牆（如 Fortinet, Palo Alto）阻擋或 DNS 遭劫持，Promise 會直接進入 catch 分支，此時便判定為受阻 ❌。
    • 超時 (Timeout)：如果客戶內網把該網域丟棄（Drop Packet）導致連線無限期等待，系統會以 AbortController 於 5 秒後強制中止，並判定為受阻。
UNIT 03

單元三：（核心重點）真實連線測試下的「DNS NXDOMAIN」與假性阻擋

1. 踩坑現況描述

在開發第一版時，顧問即使在完全沒有防火牆限制的家用網路中進行檢測，以下幾個網域依然顯示 **「受阻 ❌」**：

  • lambda.amazonaws.com
  • execute-api.amazonaws.com
  • bedrock.amazonaws.com
  • openai.azure.com
  • www.hinet.net
  • fly.dev

2. 原因剖析：DNS 解析失敗 (NXDOMAIN) 與安全阻擋

我們在終端機執行 nslookup 網域解析後，發現了根本原因：

  • A. 雲端服務的「非實體根網域」

    AWS 的服務端點是**區域型（Region-specific）**的。例如 AWS Lambda 在 DNS 中根本沒有 lambda.amazonaws.com 這個「根」紀錄（查詢會得到 NXDOMAIN，即網域不存在）。真正的實體解析端點必須是 lambda.us-east-1.amazonaws.com。

    AWS Bedrock 也是如此，根域名 bedrock.amazonaws.com 是 NXDOMAIN，必須帶有區域。而 Azure OpenAI 的網域必須包含客戶自己申請的資源前綴（如 your-resource.openai.azure.com），直接 ping openai.azure.com 是無 IP 回應的。

  • B. 通配域名安全政策與過期網域

    fly.dev 是 Fly.io 提供給開發者的通配後綴（如 appName.fly.dev），其根網域 https://fly.dev 因為安全考量，拒絕了直接的網頁請求。而 www.hinet.net 在 DNS 中已不復存在，目前中華電信主業務網域已全數移轉。

3. 解決方案：更換為「實體可解析且通暢」的公共網域

為了解決此問題，我們對測試網域進行了修正，對照表如下，這些新網域皆能在沒有防火牆的網路下 100% 通暢解析：

平台類別 原配置網域 (假性阻擋) 修正後網域 (正確連通) 修正原因說明
AWS Lambda lambda.amazonaws.com lambda.us-east-1.amazonaws.com AWS 端點為區域型，補上 us-east-1 取得 DNS A 紀錄。
AWS API Gateway execute-api.amazonaws.com apigateway.us-east-1.amazonaws.com 根域名無解析。改用區域型 API Gateway 管理端點。
AWS Bedrock bedrock.amazonaws.com bedrock.us-east-1.amazonaws.com 補上區域，防止 DNS NXDOMAIN 錯誤。
Azure OpenAI openai.azure.com management.azure.com 改用 Azure 雲資源管理入口 (ARM API) 全球公共解析端點。
Fly.io fly.dev fly.io fly.dev 根網域限制連線，改用 Fly.io 官網主域。
HiNet 虛擬主機 www.hinet.net www.cht.com.tw 原網域廢棄。改用中華電信公共官網。
HiNet 主機代管 colocation.hinet.net hicloud.hinet.net 伺服器拒絕空連線，改用 hicloud 企業雲網域。
💡 課堂教學提示

可以引導學生在終端機輸入 nslookup lambda.amazonaws.com 來親自體驗 NXDOMAIN 的回報，並對比 nslookup lambda.us-east-1.amazonaws.com 成功返回 IP 的差別，這能讓學生深刻理解 DNS A 紀錄在網路開發中的底層原理。

UNIT 04

單元四：去中心化雙向交流黑科技 —— HTML 數據內嵌技術

這套工具最酷的地方在於：顧問發出去的 HTML 評估報告，不僅能用來閱讀列印，它自己本身也是一個備份數據包！

1. 數據是如何被隱藏內嵌的？

在顧問點擊「產生 HTML 報告」時，JavaScript 會將當前記憶體中的資料封裝為 JSON，並進行 Base64 編碼，隨後寫入導出報告最底部的隱藏標籤中：

<div id="force-embedded-data" style="display:none;" data-payload="[Base64加密數據]"></div>

2. 如何反向還原 (HTML Parser)？

當顧問拿到客戶發回的 Report.html 報告並上傳時，我們在純前端使用瀏覽器內建的 DOMParser 進行解析還原：

const parser = new DOMParser();
const doc = parser.parseFromString(htmlText, "text/html");
const div = doc.getElementById("force-embedded-data");
const encodedPayload = div.getAttribute("data-payload");
const decodedJson = decodeURIComponent(escape(atob(encodedPayload)));
const parsedPayload = JSON.parse(decodedJson);

這套黑科技免去了「既要傳 HTML 報告、又要傳 JSON 資料」的雙檔案麻煩，達成了**「報告即資料，資料即報告」**的無縫協作體驗。

UNIT 05

單元五：課堂思辨與技術盲點反思（本案例之核心靈魂）

概念一：優先排除「軟體配置缺陷」，再評估「環境網路阻擋」

在實務開發或顧問現場，當我們看到一個連線顯示「受阻 ❌」時，工程師非常容易陷入直覺偏誤：「一定是客戶那邊的防火牆或安全閘道把連線擋掉了。」

  • 本案例的教訓：在第一版的網域測試中，我們在完全沒有防火牆限制的網路環境下測試，卻有多個網域回報失敗。這並非環境問題，而是我們代碼中配置了無 DNS 解析的虛擬根網域。
  • 課堂思維引導：如果顧問直接把錯誤網域清單丟給客戶網管，網管工程師配置時會發現「網域無 IP 紀錄，無法配置策略」而退件。這會立即讓客戶質疑顧問的專業度。
  • 結論：工程師必須建立**「先驗證本地配置正確性（如用 nslookup 確保 DNS 解析正常），再指控網路環境阻擋」**的標準排查思維。

概念二：AI 生成內容不等於「正確」或「符合實戰」

在生成式 AI 時代，包含大量平台與 JSON 欄位的程式碼，交給 AI 輔助生成（AI-Assisted Coding）可以在 10 秒內完成，但也帶來了關鍵盲點：

  • AI 的盲點：AI 是基於概率生成文字與代碼的。當你讓它生成 AWS 或 Azure 平台的測試網址時，它會按照語言邏輯，吐出「看起來極度合理、拼字完全正確」但實際上根本不存在於真實 DNS 系統中的網址。
  • 語法正確 vs. 實務合用：AI 生成的這段程式碼，其語法結構是 100% 正確的，但當它被放到真實網路環境下運作時，它卻是失效的。
  • 給學生的啟示：AI 是極佳的「加速器」，但它無法替工程師做「真實物理世界的狀態驗證」。這說明了：**在 AI 時代，工程師的基本功（如掌握 DNS 解析、CORS 原理、TCP 握手與 Chrome 開發者工具排查）不僅沒有貶值，反而變得更加珍貴。**
UNIT 06

單元六：網頁版權防護黑科技 —— 多層次隱形浮水印 (Watermark)

本專案在前端設計了**「多層次隱形浮水印 (Multi-layered Invisible Watermarks)」**防護機制以防範代碼被輕易剽竊：

1. HTML 註解浮水印

在 HTML 頂部和核心函數內嵌開發版權與發佈日期，防止初階複製。

2. DOM 隱身浮水印

利用 CSS 的絕對裁切技術（Absolute Clipping），建立一個存在於 DOM 樹中，但完全不佔用版面、對訪客完全不可見的 DOM 節點。當抄襲者直接複製代碼或爬蟲抓取時，該浮水印文字將會被一併複製，成為侵權鐵證。

.force-invisible-watermark {
  position: absolute;
  width: 1px;
  height: 1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  pointer-events: none;
  user-select: none;
  color: rgba(0, 0, 0, 0.001);
  background: transparent;
}

3. JavaScript 全域唯讀浮水印

利用 ES5 的 Object.defineProperty() 註冊全域變數，並將 writable 與 configurable 設為 false，防範第三方指令碼惡意覆寫或刪除版權。

Object.defineProperty(window, '__FORCE_WATERMARK__', {
  value: "Falo x Force Cheng 2026/6/22",
  writable: false,
  configurable: false
});
UNIT 07

單元七：智慧型搜尋優化與 AI 友善爬取 (GEO)

隨著 AI 搜尋引擎（Perplexity, Gemini, ChatGPT Search）普及，傳統的 SEO 已轉變為 **GEO (Generative Engine Optimization)**：

  • JSON-LD 語意化 Schema 結構化數據：在網頁 <head> 中注入 JSON-LD（宣告 @type: "SoftwareApplication"），向 AI 爬蟲精確宣告軟體名稱、作者（Force Cheng）與發布日期。
  • 結構化問答定義區 (FAQ Schema)：在評估指南中建立 FAQ 段落。AI 搜尋引擎傾向於直接摘錄有明確「問答對應 (Q&A)」的段落，這能使 AI 搜尋引擎精準提取我們網頁的 FAQ，提高引用率與排名。
UNIT 08

單元八：瀏覽器指紋追蹤與環境曝光 (Cleartext Diagnostics)

本專案特意將收集到的客戶端特徵以**「明碼 (Cleartext) / 明文」**呈現在環境診斷面板與導出的 HTML 報告中。這包含了深層的資安教學意義：

1. 偵測原理與隱私邊界

  • AdBlocker 廣告防護偵測：透過前端 fetch(adTestUrl, { mode: 'no-cors' }) 模擬請求廣告資源腳本。若連線失敗，則判定訪客啟用了 AdBlocker。這展示了如何利用「異常連線反向推導訪客軟體特徵」。
  • 設備特徵蒐集：利用 navigator.connection、navigator.deviceMemory、hardwareConcurrency、時區 API、以及 Battery API 獲取設備硬體特徵與隱私數據。

2. 資安教育思維：為什麼明碼顯示？

  • 消除技術神秘感：許多用戶以為靜態網頁（Static HTML）沒有後端資料庫就不會收集隱私。我們以明碼將數據直接呈現在用戶眼前，提醒用戶隱私特徵在靜態代碼中依然瞭若指掌。
  • 明碼傳輸風險示範：當這份報告在顧問與客戶間傳遞時，所有系統特徵均在 HTML 中明文保存。這可用於示範「敏感特徵（Metadata）未加密傳輸的資安風險」，提升學生對於數據傳輸安全（Data-in-Transit Security）的警覺度。
